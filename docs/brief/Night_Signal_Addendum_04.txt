WHY THIS ADDENDUM EXISTS

During unattended development Windows repeatedly presented Defender Firewall
approval prompts for multiple generated executables, including paths under:
- Builds/Game/NightSignal.exe
- Builds/GameSoak/NightSignal.exe
- Builds/SetupSmoke/NightSignalSmoke.exe

The user has now removed the old autogenerated Night Signal firewall rules and
created ONE explicit Private-profile UDP 7777 rule for the canonical
Builds/Game/NightSignal.exe path, named:

    Night Signal Dev LAN

Do not create, edit, delete, broaden, disable, or depend on Windows Firewall
rules automatically. The user owns firewall policy.

The current race server code still binds the gameplay transport to 0.0.0.0
while NetConfig.PublicHost defaults to 127.0.0.1. That means a routine local
test listener is exposed on all interfaces even though the advertised endpoint
is loopback. This addendum corrects that mismatch.

======================================================================
1. SEPARATE LISTEN ADDRESS FROM ADVERTISED ADDRESS
======================================================================

Do not overload one "host" concept.

Add separately named configuration:

- BindHost / ListenAddress:
  where the game-server socket actually binds.
- PublicHost / AdvertisedHost:
  what the control plane tells clients to connect to.

Required default for local development:

    BindHost = 127.0.0.1
    PublicHost = 127.0.0.1
    Port = 7777

Add an explicit command-line option equivalent to:

    -nsBindHost <address>

Retain the existing public/advertised-host option or rename only with a safe
backward-compatible migration. Existing scripts/tests must not silently swap
the meanings.

The server must call Unity Transport using BindHost for the listener. Do NOT
continue hard-coding:

    0.0.0.0

for every server process.

Using 127.0.0.1 must produce a loopback-only listener. Use an actual numeric
loopback address for deterministic Windows evidence rather than relying on
"localhost" DNS/address-family behavior.

IPv6 loopback support may be added separately if useful, but IPv4 127.0.0.1 is
the required local baseline because the current harness and control plane use
it.

======================================================================
2. LOCAL AUTOMATION IS LOOPBACK-ONLY BY DEFAULT
======================================================================

All ordinary unattended/local workflows must explicitly or effectively use the
loopback bind:

- two-client and six-client network races;
- twelve-vehicle human+AI tests;
- camera/instrument network tours;
- disconnect/reconnect/spectator tests;
- impairment tests;
- benchmark/certification network runs;
- repeated/soak multiplayer tests;
- local control-plane integration;
- any other test where every communicating process runs on the same PC.

Update Tools/run/net-race.ps1 and any sibling harnesses so their default server
launch cannot accidentally expose UDP 7777 to LAN/Public interfaces.

The harness should pass/record the intended bind explicitly, e.g.:

    -nsBindHost 127.0.0.1
    -nsPublicHost 127.0.0.1

Do not use:
- the PC's hostname;
- a LAN address;
- 0.0.0.0;
- a public IP;
- automatic "best interface" discovery

for routine local validation.

A local test is still a REAL multi-process socket test when separate processes
communicate over loopback. Do not downgrade it to an in-process fake merely to
avoid firewall prompts.

======================================================================
3. LAN/WAN LISTENING REQUIRES EXPLICIT INTENT
======================================================================

Broader listening remains supported, but must never be an accidental side
effect of launching a local test.

A deliberate LAN test may use an explicit non-loopback bind such as the
machine's Private-LAN IPv4 address or, when truly necessary:

    -nsBindHost 0.0.0.0
    -nsPublicHost <approved reachable LAN address>

Do not automatically choose 0.0.0.0 merely because LAN support exists.

For project scripts, require an explicit opt-in such as -AllowLan or an
equivalent clearly named switch before accepting a non-loopback/wildcard bind.
A raw lower-level manual server invocation may still accept an explicitly
provided BindHost, but the ordinary automated harness must protect against an
accidental wildcard.

Public/WAN exposure remains a separate acceptance gate requiring the existing
user authorization, hosting/network decisions, and appropriate security work.
This addendum does not authorize:
- router/UPnP changes;
- port forwarding;
- public cloud exposure;
- public firewall rules;
- tunneling;
- firewall profile changes;
- opening additional inbound ports.

Do not claim a loopback or LAN test proves WAN play.

======================================================================
4. NEVER MANAGE WINDOWS FIREWALL AUTOMATICALLY
======================================================================

Project code, Unity editor tooling, PowerShell test harnesses, setup scripts,
and Claude must NOT run or generate automatic commands that mutate firewall
policy, including equivalents of:

- New-NetFirewallRule
- Set-NetFirewallRule
- Remove-NetFirewallRule
- netsh advfirewall ...
- disabling Windows Defender Firewall
- enabling Edge Traversal
- silently elevating to administrator to create networking exceptions

The user's manually created "Night Signal Dev LAN" rule may remain. Local
automation must not depend on it.

If a future explicit LAN test cannot proceed because policy blocks it:
- report the exact executable, bind address, protocol, port, and intended test;
- request the minimum necessary user action;
- continue unrelated safe work where possible.

Never respond to a firewall prompt by rebuilding to another path, repeatedly
relaunching the listener, or broadening exposure.

======================================================================
6. UNATTENDED PREFLIGHT MUST FAIL CLOSED
======================================================================

Before an automated harness starts a server:

1. Resolve the intended BindHost, PublicHost, protocol, port, executable path,
   and role.
2. For the ordinary local mode, assert BindHost is loopback.
3. If it is wildcard/non-loopback without the explicit LAN opt-in, STOP BEFORE
   starting the listener with a clear error.
4. Check whether the requested UDP port is already occupied.
5. If occupied, identify the owning/likely process where practical and fail
   clearly instead of spawning repeated server processes.
6. Do not kill unrelated processes automatically merely to reclaim a port.
7. Record the resolved endpoint in the run log/evidence.

The unattended harness must not sit indefinitely waiting for a security dialog.
The primary prevention is loopback-only binding. If an OS/security prompt or
unexpected networking blocker still appears, preserve the run state and report
it as a blocker rather than repeatedly launching additional executables.

Use existing run timeouts for genuine race/test hangs, but do not mistake an
OS permission dialog for proof the game itself failed.

======================================================================
7. PROCESS AND SOCKET CLEANUP
======================================================================

At the end of an automated network run:
- request/allow normal graceful server/client shutdown first;
- enforce the existing timeout only for processes that do not exit;
- verify the test's listener is gone before a later run reuses the same port;
- leave no duplicate dedicated server processes;
- do not terminate the Unity Editor or unrelated dotnet/game processes.

A failed test must still clean up only the processes it launched.

For long repeated tests, prefer one controlled lifecycle that deliberately
starts/stops matches over uncontrolled accumulation of fresh listeners.

======================================================================
8. EVIDENCE MUST SHOW THE REAL NETWORK BOUNDARY
======================================================================

Extend network evidence/diagnostics with at least:
- executable path or stable executable role identifier;
- BindHost;
- PublicHost/advertised host;
- port;
- local/LAN/WAN test classification;
- server PID where practical;
- whether explicit LAN opt-in was present.

For the LOCAL baseline, capture Windows-side socket evidence at least once on a
built-player run showing UDP 7777 (or the chosen test port) bound to 127.0.0.1,
not 0.0.0.0 or a LAN address.

Appropriate read-only commands/tools may be used for evidence, e.g. inspecting
Get-NetUDPEndpoint or equivalent. Do not change firewall policy while collecting
evidence.

Do not call "127.0.0.1 listener verified" based only on NetConfig defaults.
Verify the actual running socket.
